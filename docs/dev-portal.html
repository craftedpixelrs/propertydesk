Pregled sistema #

PropertyDesk je multi-tenant SaaS za investitore u nekretnine i njihove partnerske agencije. Jedan Next.js App Router codebase služi i autentifikovani dashboard (my.propertydesk.app) i verziran REST API na /api/v1, plus javne surface-ove (share linkovi, microsite, marketing landing).

Postgres je jedini source of truth. Novac je uvek Decimal(14,2). Svaki tenant-owned red nosi organizationId. Agencije vide investor podatke isključivo kroz agency-safe DTO-ove — nikad kroz sirovi Prisma row spread.

Multi-tenant model

Investitor organizacija INVESTOR Projekti, inventar, CRM kupaca, rezervacije, prodaje, plaćanja, komisije, izveštaji, PDF ugovori, KYC, tax, payment plan templates. Uloge: INVESTOR_OWNER, INVESTOR_ADMIN, SALES_MANAGER, SALES_AGENT, FINANCE, INVESTOR_VIEWER.

Tenant granica je sveta Svaki service query mora da filtrira po organizationId. Cross-tenant leak je SEV 1. Nikad ne oslanjaj se na “korisnik neće videti dugme” — provera ide u requirePermission() + SQL scope.

Pravila kućnog reda #

Hard rules. Kršenje = review blok / bug u produkciji.

  1. Domain services su jedini pisci u Prisma. Route handleri ne zovu prisma.*.create/update direktno. Logika živi u src/server/services/**. Novčane i status tranzicije idu u prisma.$transaction(...).
  2. Novac = Decimal, nikad float. Kolone su Decimal(14,2). U JS-u koristi decimal.js / toDecimal / sumMoney / formatMoney. parseFloat i IEEE float za novac su zabranjeni.
  3. Svaki tenant query scoped na organizationId. Nema “globalnih” lista za investor podatke. Ako zaboraviš filter — to je security bug, ne feature.
  4. Agencije dobijaju samo agency-safe DTO. Mapiranje u src/server/services/agencies/dtos.ts (ili ekvivalent). Nikad ne šalji sirovi Unit / Sale row agencijskom klijentu.
  5. Server-only moduli ostaju na serveru. Fajlovi koji importuju Prisma, secrets, audit, PDF ili auth config moraju imati import "server-only" (ili biti ispod src/server/ putanje koju bundler ne vuče u client).
  6. Permissions samo preko requirePermission("resource.action"). Zabranjeno: if (role === "INVESTOR_OWNER") u business kodu.
  7. UI copy uvek sr-Latn. Engleski stringovi u dugmadima/toastovima/labelama = bug.
Audit je append-only Mutacije koje menjaju status, novac, članstvo ili impersonation moraju zvati recordAudit(). Nema update/delete API-ja za audit redove.

Request lifecycle #

Svaki mutacioni / autentifikovani REST poziv prati ovaj lanac:

UI (RSC / client fetch) → Route src/app/api/v1/**/route.ts → apiHandler({ bodySchema, paramsSchema, … }) · parse Zod · requestId + x-request-id header · rate-limit (ako uključeno) → requirePermission("resource.action") · session (Better Auth) · active organization · role → permission matrix / overrides → domain service (src/server/services/**) → prisma.$transaction (novac / status) → recordAudit({ action, entityType, … }) → envelope { data, meta } ili ApiError envelope

Brojčano:

  1. UI — feature komponenta zove api-client ili server action koji ide na REST.
  2. Route — tanak controller; samo wiring.
  3. apiHandler — validacija, envelope, mapiranje grešaka, Sentry na 5xx.
  4. requirePermission — authz kontekst (AuthorizedContext).
  5. Service — poslovna pravila, Decimal, org scope.
  6. Prisma tx — atomičnost.
  7. Audit — append-only trag.

Permissions model #

Dva sloja autorizacije

PropertyDesk ima tri odvojena autorizaciona sloja. Nikad ih ne mešamo u istoj tabeli, istom ekranu ili istom API pozivu.

Sloj Šta rešava Gde je izvor istine Admin ekran
Sloj A — Platforma / Nalog „Da li nalog uopšte ima pristup?" user.role (SUPER_ADMIN), saas_plan, organization_subscription, organization_profile.status, global_billing_settings /administracija/organizacije, /administracija/planovi, /administracija/naplata
Sloj B — Aplikacija „Šta ulogovan član radi unutar svoje org?" member.role + matrica u src/server/permissions/roles.ts + role_permission_override /administracija/role (uređivač matrice), /podesavanja/korisnici (dodela role članovima)
Sloj C — Property Desk internal team „Ko iz našeg tima marketira i prodaje sam SaaS?" property_desk_team_member (teamRole, leadScope, enabled), marketing_lead pipeline /administracija/property-desk, /administracija/property-desk/tim, /administracija/property-desk/leadovi

Kanonska definicija dozvola je u src/server/permissions/access-control.ts. Enforcement za Sloj A/B: requirePermission / requirePlatformPermission. Enforcement za Sloj C: requirePropertyDeskAccess / requirePdPermission(ctx, "pd_*") / hasPdPermission(ctx, "pd_*") / canViewMarketingLead(ctx, lead) u src/server/permissions/property-desk.ts. Sve dozvole iz porodice pd_* se editovanjem prolaze kroz isti override sloj kao aplikacione uloge, tako da se ponašanje SETTER-a, CLOSER-a, OPERATIONS-a i MANAGER-a menja iz UI-ja bez redeploy-a. Sloj C ne meša se sa tenant Member.role — svako je samostalna dimenzija.

Property Desk leveli i forward-only pipeline. MarketingLead.level (SOURCING, CLOSING, OPERATIONS, ARCHIVED) se deriviše iz stage preko STAGE_TO_LEVEL u src/server/services/property-desk/lead-lifecycle.ts. canViewMarketingLead i buildMarketingLeadScopeFilter prvo filtriraju po ROLE_LEVELS[teamRole], pa tek onda po leadScope — SETTER vidi samo SOURCING, CLOSER samo CLOSING, OPERATIONS samo OPERATIONS, MANAGER sve. Stage tranzicije su jednosmerne (FORWARD_TRANSITIONS); sve što nije forward zahteva novu dozvolu pd_lead.reopen (default samo MANAGER + SUPER_ADMIN) i neprazan reopenReason, i pored audit reda marketing_lead.reopened upisuje SYSTEM aktivnost u timeline. Prelazak preko granice levela automatski postavlja previousLevel, levelEnteredAt i assignedToUserId = null (auto-unassign u pool sledećeg levela).
Bogatiji lead + deterministički score. MarketingLead ima nova opciona polja: klasifikacija (priority, temperature, timelineHorizon, nextFollowUpAt, leadScore), firma (companyName, companyWebsite, companySize), novac (budgetTier, budgetCurrency), donosilac odluke (decisionMakerName, decisionMakerTitle, preferredContact, bestContactHour), kvalifikacija (competitor, painPoint) i geo (country, region, preferredLanguage). Nova dozvola pd_lead.update_classification (default svim PD članovima) pokriva priority/temperature/timeline/nextFollowUp; canWriteLead osigurava da SETTER/CLOSER/OPERATIONS mogu da pišu samo u lead-ove svog levela. Score se računa deterministički u src/server/services/property-desk/lead-scoring.ts (cap 100) i osvežava se automatski na create/update, uz opciju eksplicitnog override-a kroz update_classification.
Publika je zaključana; L3 pravi tenant. Kad je audience jednom INVESTOR ili AGENCY, polje se ne sme menjati (servis baca INVALID_STATE). Na L3 (WON) Super Admin i Operations iz detalja lead-a vežu postojeću org. ili prave novu + vlasnika (INVESTOR_OWNER / AGENCY_OWNER) sa paketom — POST /platform/property-desk/leads/{id}/convert prima organizationId ili createOrganization. Closer i dalje sme samo da veže postojeći tenant (što prebacuje lead u L3 pool).

Better Auth i sesije #

Autentifikacija je centralizovana u src/server/auth/auth.ts (Better Auth + Prisma adapter). Sesija je HTTP-only cookie; tenant kontekst dolazi isključivo iz activeOrganizationId na session redu — nikad iz query/body parametra.

Login i session cookie

Email+password sa verifikacijom (requireEmailVerification: true). U produkciji cookie prefix je propertydesk sa useSecureCookies: true, pa session token izgleda kao __Secure-better-auth.session_token (Better Auth interno ime). Trajanje: 7 dana, refresh jednom dnevno (updateAge: 24h). Cookie cache TTL je 30s — kratko da promene role/active org brzo stignu do klijenta. 

// Browser — authClient iz @/lib/auth-client
await authClient.signIn.email({ email, password });
await authClient.organization.setActive({ organizationId });

Organizations plugin

Jedan Organization = jedan tenant. Plugin upravlja članstvima (member), pozivnicama i prebacivanjem aktivne org. Tip profila (INVESTOR / AGENCY) živi u OrganizationProfile. Detalji multi-tenant modela: Pregled sistema.

requireSession() i requirePermission()

API rute koriste lanac iz src/server/auth/session.ts i src/server/permissions/require.ts: 

const ctx = await requirePermission("sale.read");
// ctx.session — Better Auth session
// ctx.organization — { organizationId, organizationRole, organizationStatus, … }
// ctx.isSuperAdmin — platform bypass (audit i dalje obavezan)
  • requireSession() — baca UNAUTHENTICATED (401).
  • requireActiveOrganization() — baca NO_ACTIVE_ORGANIZATION ako nema izabrane org.
  • requirePermission("…") — proverava role matrix + override sloj; u RESTRICTED billing režimu dozvoljava samo allowlist (vidi Permissions model).

Izbor aktivne organizacije

Izvor istine: session.activeOrganizationId, cross-check protiv member tabele u getActiveOrganization(). Fallback redosled: DB session → jedina membership → null (SUPER_ADMIN bez tenanta ide na /administracija). UI: org switcher poziva authClient.organization.setActive.

SUPER_ADMIN impersonate

Admin plugin (impersonate permission samo za platform role). Flow: launcher na /administracija/korisnici → Better Auth mintuje sesiju sa impersonatedBy → dashboard prikazuje ImpersonationBanner (src/components/app/impersonation-banner.tsx). Audit: platform.impersonation_started na startu; svaki recordAudit može nositi impersonatedByUserId — vidljivo na /administracija/revizija.

Bez curenja identiteta Tokom impersonacije session.user je ciljni korisnik — logika mora koristiti impersonatedBy za “ko je stvarno kliknuo”, ne session.user.id za platform akcije.

server-only / use client #

Next.js App Router razdvaja Server Components (podrazumevano) i Client Components ("use client"). Pravilo: sve što dira Prisma, tajne, ili file-system ide u server sloj.

Kada šta

SlojDirektivaPrimeri
Server Component / route / service import "server-only" na vrhu fajla *.service.ts, session.ts, storage/index.ts
Client Component "use client" Forme, chart interakcija, authClient, apiClient
Shared pure util Nijedna (bez side-effect-a) src/lib/formatters/*, Zod šeme bez DB

Sprečavanje curenja Prisma klijenta

  1. Prisma client samo u src/server/db/prisma.ts — importuj ga isključivo iz src/server/**.
  2. Dodaj import "server-only" u svaki server modul koji exportuje DB pristup.
  3. Ne importuj server service u Client Component — pozovi /api/v1/… preko apiClient.

Auth / dozvole u Swaggeru

Swagger je i dokumentacija dozvola: svaka operacija mora u description da ima prvi red **Auth:** \`…\` koji odgovara handleru (vidi Permissions model).

  • requirePermission("resource.action") — org RBAC (+ overrides).
  • requireSuperAdmin() / requirePlatformPermission("…") — platform SUPER_ADMIN.
  • sesija (ulogovan + aktivna org) — ulogovan, bez posebne permission.
  • javno / javno + rate-limit / Better Auth — bez sesije ili auth cookie flow; public operacije imaju security: [].
  • CRON_SECRET — Bearer ili x-cron-secret.

Posle izmene auth helpera u ruti: ponovo pnpm docs:swagger:perms, zatim pnpm docs:swagger:spec i pnpm docs:swagger:check (očekuj without: 0).

Specifikacija koja je obavezna

  • Svaka operacija: **Auth:** \`…\` u operation-level description (ne u responses.*.description).
  • Svi POST/PATCH endpointi: tačna Zod shema u requestBody (ne additionalProperties: true).
  • Sve 422 VALIDATION_ERROR moraju da navedu fieldErrors mapu.
  • Public endpointi (/api/public/*, /api/auth/*, /api/docs, health) imaju security: [].
  • Sve 429 odgovore imaju Retry-After header naveden.

BigInt Mod-97 gotcha

IPS “poziv na broj” koristi model 97 (Mod-97). Telo je 12-cifreni broj; check digit: check = 98 - (n % 97), format 97 CC-NNNNNNNNNNNN.

Obavezno BigInt 12-cifreni broj prelazi bezbedan JS Number integer opseg za tačan modulo. Koristi BigInt u generateIpsReference(). Number/float daje pogrešan check digit i pada bankarska validacija — postoji regresioni test baš zbog starog TypeError / pogrešnog modula. 
// skraćeno — ideja, ne copy-paste iz produkcije
const body = "123456789012"; // 12 cifara
const n = BigInt(body);
const check = Number(98n - (n % 97n));
const cc = String(check).padStart(2, "0");
const ref = `97 ${cc}-${body}`;

NBS payload oblik: K:PR|V:01|C:1|R:… (vidi docs/billing/ips-qr.md).

FIFO alokacija uplata #

Jedna uplata može pokriti više otvorenih faktura (SaaS billing) ili, konceptualno, više rata — algoritam je isti: computeFifoAllocations u src/server/services/billing/payments/allocation.service.ts. Poziva ga recordPayment u billing payments servisu i bank-statement matcher.

Algoritam (rata po rati)

  1. Uzmi sortirane otvorene stavke (fakture: dueDate ASC, zatim createdAt).
  2. Inicijalizuj remaining = amount uplate.
  3. Za svaku stavku sa istom valutom i amountDue > 0: take = min(due, remaining), upiši alokaciju, smanji remaining.
  4. Preostalo → unappliedAmount (neapplied kredit na uplati).

Primer: 3 rate / fakture, uplata preko sume

// Rate A: 60 EUR, Rate B: 60 EUR, Rate C: 40 EUR
// Uplata: 100 EUR
// → A: 60, B: 40, unapplied: 0

// Uplata: 150 EUR (sve tri rate ukupno 160)
// → A: 60, B: 60, C: 30, unapplied: 0

// Uplata: 200 EUR
// → A: 60, B: 60, C: 40, unapplied: 40

Regresioni testovi: allocation.service.test.ts. API response polje unappliedAmount vraća recordPayment u billing/payments/service.ts.

Storno

Uplate se ne brišu. Storno (reversePayment) postavlja status: REVERSED, reversedAt, obavezan reversalReason — audit billing.payment_reversed. Alokacije se poništavaju (invoice amountPaid / amountDue se vraćaju); originalni PaymentAllocation redovi se uklanjaju iz aktivnog stanja, istorija ostaje na payment redu. Sale-side storno: reversedAt na Payment + re-propagation rate/plan statusa (Payment plan templates).

Immutability Finansijski trag je append-only po duhu — nema hard delete uplate ni alokacije iz produkcijskog UI-ja.

Buyer protection #

Agencija registruje kupca na projektu investitora; investitor odobrava. Zaštita traje N dana po konekciji (tipično 60; schema default 30 — podešava se per AgencyConnection.defaultProtectionDays pri approve). Servis: registrations.service.ts.

60 dana ekskluziva per-connection

Aktivni statusi: PENDING, APPROVED. protectionEndsAt = approvedAt + protectionDays. Konflikt se proverava po normalizovanom telefonu/emailu na istom projectId, druga agencija.

409 CONFLICT_REVIEW

Kada druga agencija pokuša registraciju za istog kupca, API vraća fiksnu srpsku poruku bez identiteta druge agencije (CONFIDENTIAL_CONFLICT_MESSAGE). Interno se upisuje red sa status: CONFLICT_REVIEW — investitor vidi ga na /agencije/registracije sa anonimizovanim payload-om prema agenciji.

0 * * * * (hourly) — expireDueProtections() prebacuje istekle APPROVED u EXPIRED. Idempotentno. Vidi Cron tabela.

  • Ista agencija ponovo registruje istog kupca — reuse buyer reda.
  • Kupac bez normalizovanog telefona ni emaila — conflict check preskočen (edge case).
  • Registracija već EXPIRED / REJECTED — nova registracija dozvoljena.

Docker notes #

Produkcijski image je multi-stage. Bitna gotcha: pnpm izolacija lomi prisma migrate deploy u runner-u.

prisma-cli flat npm install trick Builder instalira ravno stablo u /prisma-cli/node_modules preko npm (prisma + @prisma/config + dotenv + tsx), pa runner COPY-uje to preko app node_modules/. Bez toga migrate u kontejneru često ne nalazi transitive deps (effect, c12…). Vidi komentare u Dockerfile i .npmrc public-hoist-pattern.
  • Prod build: next build --webpack (ne Turbopack).
  • Build-time placeholder DATABASE_URL / DIRECT_URL.
  • TS drop-in 5.7.2 u Docker buildu zbog Next kompatibilnosti (lokalno može TS 7).
  • Standalone output → node server.js u runner-u.
